## JSON rules in one minute
JSON (RFC 8259) supports objects, arrays, strings, numbers, true, false and null. Keys and strings must use double quotes, there are no comments, and the last item in an object or array must not have a trailing comma. Text should be UTF-8. These rules make JSON easy for every language to parse, from JavaScript and Python to Go, Rust and Swift.
## Minify or beautify?
Beautified JSON is for humans: code reviews, documentation and debugging. Minified JSON removes all optional whitespace and is typically 10–30% smaller, which helps with storage, caching and network transfers, although gzip or Brotli compression on web servers narrows the gap. Keep a formatted copy in version control and minify at build time.

## How Base64 works
Every three bytes of input (24 bits) are split into four groups of six bits, and each group is mapped to one of 64 characters: A–Z, a–z, 0–9, + and /. When the input is not a multiple of three bytes, = signs pad the end. Because text is converted to UTF-8 bytes first, “é” becomes two bytes and “👍” four, which is why short non-English strings can produce longer Base64.
## Common pitfalls
Many simple tools use the browser's btoa function directly, which fails on any character outside Latin-1. This encoder converts text to UTF-8 first, matching how servers and most programming languages behave. If decoded text looks garbled, the original data was probably binary (an image or a zip) or used a different character set, such as Windows-1252 or Shift_JIS.

## Percent-encoding explained
Each unsafe byte is written as % followed by two hexadecimal digits. Text is first converted to UTF-8, so “café” becomes caf%C3%A9 and “東京” becomes %E6%9D%B1%E4%BA%AC. Letters, digits and - _ . ~ are never encoded. Reserved characters such as : / ? # [ ] @ ! $ & ' ( ) * + , ; = have special meaning and must be encoded when used as data.
## Internationalised links
Modern browsers display Unicode in the address bar, but the underlying request always uses percent-encoded paths and Punycode for domain names. When you share links in emails, documents or QR codes, the encoded form is the most reliable and works with every app and device.

## v4 or v7?
Version 4 UUIDs are completely random, which is ideal when you do not want identifiers to reveal anything. Version 7, standardised in RFC 9562 in 2024, starts with a 48-bit Unix timestamp in milliseconds followed by random bits. Records created later get larger IDs, so B-tree indexes in PostgreSQL, MySQL and SQL Server stay compact, and you can roughly tell when a record was created.
## Format variations
The canonical form is 32 lowercase hexadecimal digits in groups of 8-4-4-4-12. Some systems want them without hyphens (32 characters), in uppercase, or wrapped in braces. The nil UUID, all zeros, is used as a placeholder for “no value”.

## Colour models in brief
RGB mixes red, green and blue light and is how screens work. HEX is simply RGB written in hexadecimal. HSL and HSV describe colour by hue (0–360°), saturation and lightness or brightness, which is more intuitive for adjusting colours. CMYK describes cyan, magenta, yellow and black inks for print. Conversions between RGB-based models are exact; CMYK is an approximation without a colour profile.
## Accessible colour choices
Around 1 in 12 men and 1 in 200 women have some form of colour vision deficiency, and many people read screens in bright sunlight. Good contrast helps everyone. The contrast ratios here follow the WCAG formula based on relative luminance, the same method used by Lighthouse and accessibility checkers, and they are required by laws and standards such as the European Accessibility Act and the ADA.
